# REQ-11 전체 시스템 (api - agent - executor - batch - runtime) 연계

| 항목 | 값 |
| --- | --- |
| 요구사항 번호 | 11 |
| 서비스구분 | REQ 요구사항 |
| 우선순위 | P0 |
| 화면 | 일부 화면 + 보조 확인 |
| 필요 권한 | 일반 + 운영 |
| 단독 수행 | 아니오 |
| 관련 통합테스트 시나리오 | PREP-08, RUN-01, RUN-02, RUN-03, BAT-01, BAT-02, BAT-03, BAT-04, EXEC-08 |

## 1. 목적
한 번의 분석 요청과 그 결과로 만든 배치가 API → Agent(워커) → executor → Jupyter 런타임, 그리고 pr-batch → executor → 리포트까지 끊기지 않고 이어지며, 각 서비스의 기록이 같은 사용자·세션·run으로 묶이는지 확인합니다.

## 2. 사전 조건
- 세 서비스(pr-agentic-service, executor, pr-batch)와 Redis 정상, 연결 스모크 통과(PREP-08)
- 일반 A 로그인, 관리자 1명, 운영 담당(로그 확인)
- ACTIVE 런타임 1개 이상

## 3. 수행 절차
처음 수행하는 사람은 아래 3-1절 "화면 조작 안내"를 먼저 읽습니다. 번호 줄은 할 일이고, 그 아래 작은 항목은 실제로 누르고 입력하고 확인할 내용입니다. "※ 미확인"은 코드로 확인하지 못해 환경에서 한 번 확인이 필요한 내용입니다. 우리 화면(`/dev/`)은 테스트를 수행하기 위한 보조 도구이고 통합 테스트 대상이 아닙니다. 통과·실패는 서버 응답(상태 코드, 응답 본문, 이벤트)과 세 서비스의 기록으로 판정하고, 화면에 보이는 글자나 버튼은 그 값을 읽는 수단으로만 씁니다.

1. 관리자로 **시스템** 화면에서 executor와 런타임 상태를 확인합니다.
   - **시스템 > 런타임** 탭에 ACTIVE 런타임이 있고, **점검** 탭에 진행 중인 점검이 없는지 봅니다(`GET /api/v1/executor/runtime-targets`, `/executor/maintenance` 200).
2. A로 새 대화에서 "nce 데이터 불러와서 LOT별 SN OPEN 평균을 비교해줘"를 보내고 끝까지 진행합니다.
   - `POST /api/v1/sessions/<세션 ID>/runs` 응답의 상태 코드와 응답 헤더 `X-Request-ID`를 적습니다(요청·응답 창 > 헤더).
   - 세션 ID, run ID를 복사합니다. 계획과 코드 실행을 승인합니다.
3. 요청·응답 창에서 run 상태 변화를 순서대로 적습니다.
   - `run_status` 이벤트가 `queued` → `running` → `waiting_input`(계획 승인) → `running` → `waiting_executor`(코드 실행) → `running` → `succeeded` 흐름인지 봅니다. 빠르게 지나간 상태는 못 봐도 순서가 맞으면 됩니다.
4. **실행 이력**에서 그 실행의 **개요**를 봅니다.
   - 사용자가 A의 사번, 프로젝트·세션이 이 대화의 ID, "run (metadata.run_id)"가 2번의 run ID, tenant가 `dtest-agent-service`, 런타임 칸에 값이 있는지 봅니다.
5. 답변 첨부의 노트북으로 배치 스크립트를 등록하고 배치를 만들어 **지금 실행**합니다.
   - BAT-01~03과 같은 절차입니다. 노트북 artifact ID로 **배치 > 스크립트 등록**, **새 배치**(이름 `it-req11`, 일정 간격 60분), 목록에서 **지금 실행**을 누릅니다.
   - 실행 이력 창에서 상태가 `SUBMITTED` → `RUNNING` → `COLLECTING` → `COMPLETED`로 가는지 봅니다.
6. 끝난 배치 실행 줄을 눌러 executor 실행 **개요**를 봅니다.
   - 방식에 `BATCH`, 사용자가 A의 사번, `created_by_client`가 pr-batch의 키 이름인지 봅니다.
7. 배치 리포트가 만들어지는지 봅니다.
   - `GET /api/v1/batch-reports?batch_id=<배치 ID>` 응답에서 그 실행의 리포트 `status`가 `SUCCEEDED`가 되는지 봅니다(최대 30분).
8. 운영 담당이 2번의 request id로 로그를 찾습니다.
   - 우리 서비스 로그에서 `request_id=<2번 값>`을 검색합니다. 같은 id가 executor 로그에도 있는지 executor 담당에게 요청합니다.

## 3-1. 화면 조작 안내

**접속과 로그인**
- 브라우저는 Chrome 또는 Edge를 씁니다. 주소창에 우리 화면 주소 `https://<host>/dev/`를 넣습니다. `<host>`는 환경마다 다르므로 테스트 담당이 공지한 dev 또는 prd 주소를 씁니다.
- 주소를 열면 회사 SSO 로그인 화면으로 넘어갑니다. 사번과 비밀번호로 로그인하면 우리 화면으로 돌아옵니다. "로그인하지 못했습니다"가 나오면 **다시 로그인**을 누르고, 그래도 안 되면 수행을 멈추고 운영 담당에게 알립니다.
- 지금 누구로 들어와 있는지는 화면 왼쪽 맨 아래 이름 칸에서 봅니다. 이름 아래에 사번이 있고, 칸을 누르면 "사번 … · 관리자" 또는 "사번 … · 일반 사용자"와 **로그아웃**이 나옵니다. 관리자는 이름 옆에 "관리자" 표시가 붙고 왼쪽 메뉴에 **시스템**이 보입니다.
- 이 문서의 계정 이름: **관리자**는 PREP-09에서 관리자로 로그인한 사번, **일반 A**와 **일반 B**는 테스트용 일반 사번 두 개입니다. 어느 사번이 A, B인지는 테스트 담당이 정해 둔 값을 씁니다.
- 사번을 입력하는 칸에는 항상 소문자로 넣습니다(예: `a10054`).

**화면 구성**
- 왼쪽 메뉴는 위에서부터 **새 대화**, **프로젝트**, **워크플로우**, **실행 이력**, **배치**, (관리자만) **시스템**입니다. 그 아래가 대화 목록, 맨 아래가 내 이름 칸입니다.
- 오류가 나면 화면 위쪽에 빨간 오류 메시지가 뜹니다. 메시지에는 오류 코드와 "요청 ID …"가 붙어 있고, 요청 ID를 누르면 복사됩니다. 결함을 적을 때 이 요청 ID를 함께 적습니다.

**ID와 사번 구하는 법**
- **프로젝트 ID, 세션 ID, run ID**: 대화를 열면 화면 위 대화 이름 옆에 "프로젝트 xxxxxxxx", "세션 xxxxxxxx", "런 xxxxxxxx" 꼬리표가 있습니다. 앞 8자리만 보이지만 꼬리표를 누르면 전체 ID가 복사됩니다("복사됨"으로 잠깐 바뀜). 메모장에 붙여 두고 씁니다.
- **사번**: 그 사람이 로그인한 화면의 왼쪽 맨 아래 이름 칸에 있습니다. 관리자는 **시스템 > 사용자**에서 이름으로 찾아 사번 칸을 볼 수도 있습니다.
- **기본 프로젝트 ID**: 요청·응답 창에서 `users/me`로 거른 뒤 `GET /api/v1/users/me` 줄의 응답 본문에서 `default_project_id` 값을 복사합니다.
- **실행 ID, 배치 ID 등 표의 짧은 ID**: 표에 8자리로 보이는 ID는 누르면 전체가 복사됩니다.

**요청·응답 창 보는 법**
- 화면 오른쪽 위 구석의 **요청·응답 N** 버튼을 누르거나 Ctrl+`(숫자 1 왼쪽 키)를 누르면 열립니다. 이 화면이 서버에 보낸 요청과 받은 응답이 최신 순으로 쌓입니다.
- 목록 한 줄은 시각, 방식(GET·POST 등), 경로, 상태 코드, 걸린 시간입니다. 줄을 누르면 오른쪽에 **요청 본문**, **응답 본문**(각각 **복사** 버튼), 접혀 있는 **헤더**가 나옵니다.
- 원하는 요청을 찾으려면 위쪽 "경로·메서드·상태로 거르기" 칸에 경로 일부(예: `users/me`)나 상태 코드(예: `403`)를 넣습니다.
- **현재 대화만**이 켜져 있으면 지금 열어 둔 대화의 요청만 보입니다. 채팅이 아닌 화면(시스템, 배치, 실행 이력)의 요청이 안 보이면 이 체크를 끕니다.
- **SSE**가 켜져 있으면 경로가 `/sessions/…/events`인 줄이 보입니다. 이 줄을 누르면 "받은 이벤트 N건"이 최신 순으로 나오고, 이벤트마다 종류(`run_status`, `hitl_request`, `execution_completed`, `artifact` 등)와 내용이 있습니다.
- **오류만**을 켜면 실패한 요청만 남고, **지우기**는 목록을 비웁니다. 확인하려는 동작 직전에 **지우기**를 누르면 찾기 쉽습니다.

**채팅 화면 쓰는 법**
- 어느 프로젝트에서 대화할지 먼저 정합니다. 왼쪽 **프로젝트**를 누르고 쓸 프로젝트 카드를 누릅니다("기본" 표시가 있는 것이 처음 로그인 때 만들어진 프로젝트).
- 왼쪽 **새 대화**를 누르면 "무엇을 분석해 볼까요?" 화면이 나옵니다. 아래 입력창("분석하고 싶은 내용을 입력하세요")에 문장을 넣고 Enter를 누르거나 오른쪽 화살표 버튼을 누르면 전송됩니다. 줄을 바꾸려면 Shift+Enter입니다.
- 입력창 아래에 왼쪽부터 이미지 첨부, **모델** 선택, **코드 레벨** 선택이 있습니다. 따로 말이 없으면 모델은 처음 값 그대로, 코드 레벨은 "코드 레벨 · 기본"으로 둡니다.
- 보낸 뒤에는 "생각하는 중", "코드 실행 중 · N단계", "확인을 기다리는 중" 같은 진행 표시가 나옵니다. 이 동안 전송 버튼은 **중지** 버튼(네모)으로 바뀝니다.
- 끝나면 답변이 나오고, 분석을 실행했다면 답변 아래에 첨부가 붙습니다. "MD"는 리포트, "IPYNB"는 노트북이고 각각 **보기** 링크로 새 탭에서 열립니다. 답변 아래의 "런 xxxxxxxx" 꼬리표가 그 답변의 run ID입니다.
- 왼쪽 대화 목록에서 대화를 누르면 다시 열립니다. 대화 줄에 마우스를 올리면 이름 바꾸기와 삭제 아이콘이 나옵니다.

**확인 카드에 답하는 법**
- 에이전트가 사용자 확인이 필요하면 화면 오른쪽에 카드가 열리고, 채팅에는 "… · 오른쪽 패널에서 확인해 주세요" 줄이 생깁니다. 카드 맨 위 제목으로 종류를 구분합니다.
- **실행 계획 확인** (plan_approval): 위에 "후보 N개"가 나오고 후보마다 번호 탭이 있습니다. "추천 워크플로우" 표시가 붙은 후보는 등록된 워크플로우에서 온 것입니다. 후보를 누르면 단계가 skill별로 묶여 `#번호 tool 이름` 줄로 나오고, 줄을 누르면 입력값이 펼쳐집니다. "입력 필요"가 붙은 칸은 값을 넣어야 합니다. 맨 아래에 **수정 요청**(왼쪽 칸에 요청을 적고 누름), **취소**, (있을 때만) **추천 말고 새로 만들기**, **승인하고 실행**이 있습니다. 따로 말이 없으면 1번 후보를 그대로 두고 **승인하고 실행**을 누릅니다.
- **코드 실행 승인** (code_approval): 에이전트가 쓴 코드가 보입니다. 맨 아래 **실행**을 누르면 승인, **거절**을 누르면 거절입니다.
- **질문** (question): 선택지 버튼이 있으면 하나를 누르고, 없으면 "직접 답변 입력" 칸에 답을 적고 **답변**을 누릅니다.
- **워크플로우 저장** (workflow_save): 이름과 예시 질문이 채워져 있습니다. **저장** 또는 **저장 안 함**을 누릅니다.
- 카드에 답하면 카드가 닫히고 진행이 이어집니다. 카드 한 장이 한 번의 확인이며, 요청·응답 창에서는 `hitl_request` 이벤트로 보입니다. 이 이벤트 내용의 `interrupt_id`가 그 카드의 ID입니다.

**실행 이력 보는 법**
- 왼쪽 **실행 이력**을 누르면 executor가 돌린 실행 목록이 나옵니다. 일반 사용자는 자기 것만, 관리자는 전체 사용자의 것을 봅니다.
- 위쪽 거르기 줄: (관리자만) tenant 선택과 "사용자 (이름·사번·ID)" 칸, 프로젝트 선택, "세션 ID" 칸, "실행 ID로 바로 열기" 칸(ID를 넣고 Enter), 상태 선택, 종류 선택(**채팅 분석** / **배치** / **채팅 + 배치**), **조회** 버튼입니다. 칸을 채운 뒤 **조회**를 눌러야 반영됩니다.
- 표의 칸은 상태, 실행(ID 앞 8자리), 사용자, 프로젝트 / 세션, 방식, 단계, 시작, 종료, 소요입니다. 방금 한 실행은 맨 위에 있습니다.
- 줄을 누르면 실행 상세 창이 열립니다. 탭은 **개요**, **단계**, **이벤트**, **결과**, **노트북**, **산출물**이고 관리자에게는 **진단**, **시도**가 더 보입니다.
- **개요**에는 실행 ID, 상태, 방식, tenant, 요청자(created_by · created_by_client), 사용자, 프로젝트, 세션, run (metadata.run_id), 런타임이 있습니다. 맨 아래 **원본 JSON**을 누르면 executor가 준 내용 전체가 펼쳐집니다.
- 창은 오른쪽 위 **닫기**로 닫습니다.

**끝난 뒤 기록**
- 각 단계에서 예상 결과와 비교할 화면을 캡처합니다(Windows는 Win+Shift+S). API 키 원문, 쿠키, CSRF 토큰이 보이면 가리고 올립니다.
- 이 페이지 7절 "수행 기록"에 환경, 수행자, 수행 일시, 빌드 커밋, 결과를 적고, 8절에 단계별 실제 결과와 증빙(캡처, 응답 본문, request id, run id, 실행 ID)을 붙입니다.
- 상황판(엑셀)에서 이 요구사항의 TC 줄마다 상태를 **통과** 또는 **실패**로 바꾸고 시작일자와 완료일자를 적습니다. 4절 예상 결과의 한 줄이 TC 하나입니다.
- 판정 근거는 서버가 준 값입니다. 4절 예상 결과에 화면 표시로 적힌 항목도 요청·응답 창의 응답 본문이나 이벤트에서 같은 값을 확인해 판정합니다. 화면만 이상하고(글자 깨짐, 버튼 위치, 새로 고침해야 보임 등) 서버 응답은 예상과 같으면 **통과**이고, 화면 문제는 결함으로 올리지 않고 테스트 담당에게 따로 알립니다.
- 화면으로 수행할 수 없게 되면(화면이 열리지 않음 등) 같은 요청을 **시스템 > API 호출 시험**이나 curl로 보내 수행해도 됩니다.
- 예상과 다르면 더 진행하지 말고 상태를 **실패**로 두고 9절에 결함(재현 단계, 예상, 실제, 발생 시각, request id)을 적은 뒤 결함번호를 상황판에 넣습니다.

## 4. 예상 결과
- 2 (REQ-11-01 API가 분석 요청을 받아 run 생성): `POST /sessions/{id}/runs` 202, 응답에 run ID, 응답 헤더 `X-Request-ID` 값
- 3 (REQ-11-02 Agent(워커)가 run을 끝까지 진행): `run_status`가 `queued`에서 시작해 `waiting_input`, `waiting_executor`를 거쳐 `succeeded`로 끝남
- 4 (REQ-11-03 executor 실행 기록이 사용자·세션·run과 묶임): 실행 상태 `SUCCEEDED`, 사용자 = A의 사번, `metadata.run_id` = run ID, tenant `dtest-agent-service`, 런타임 값 있음
- 5 (REQ-11-04 채팅 결과 노트북이 pr-batch 배치로 실행): 스크립트 등록·배치 생성 2xx, 배치 실행 상태가 `COMPLETED`로 끝남
- 6 (REQ-11-05 배치 실행이 executor에 A의 이름으로 기록): 방식 `BATCH`, 사용자 = A의 사번, `created_by_client` = pr-batch 키 이름
- 7 (REQ-11-06 배치 리포트 생성): `/batch-reports` 응답의 그 실행 리포트 `status: SUCCEEDED`, `artifact_id` 값
