# 통합테스트 시나리오 페이지 양식

시나리오마다 컨플루언스 페이지를 하나 만들고, 상황판의 링크 칸에 그 주소를 넣습니다. 위쪽(1~6)은 테스트 설계자가 미리 쓰고, 아래쪽(7~9)은 수행자가 수행할 때 채웁니다. 맨 아래에 샘플 3개가 있습니다.

## 양식

```
# <ID> <시나리오명>

| 항목 | 값 |
| --- | --- |
| 서비스구분 | <영역> |
| 우선순위 | P0 / P1 |
| 화면 | O 화면만 / 일부 화면 + 보조 확인 / X 화면 밖 |
| 필요 권한 | 일반 / 관리자 / API 도구 / 운영 / gaia 화면 |
| 단독 수행 | 예 / 아니오 (예: 시간을 정해 혼자 수행) |
| 연동 경로 | I1 ~ I9 |

## 1. 목적
이 시나리오로 무엇을 확인하는지 한두 문장.

## 2. 사전 조건
- 계정: 어떤 사번(관리자 / 일반 A / 일반 B)
- 키·데이터: 필요한 API 키, 테스트 데이터, 배치·스크립트
- 먼저 끝나야 할 시나리오: <ID>
- 환경 상태: 켜져 있어야 하는 서비스, 설정값

## 3. 수행 절차
번호를 붙여 한 동작씩. 화면은 메뉴 경로와 버튼 이름을 그대로, API는 복사해 쓸 수 있는 명령을.
1. ...
2. ...

## 4. 예상 결과
단계 번호별로. 문장이 아니라 확인할 수 있는 값으로 씁니다(상태 값, 오류 코드, 카드·이벤트 종류, 화면 표시).
에이전트 답변 문구는 매번 달라지므로 판정에 쓰지 않습니다.

## 5. 확인 방법
어디서 무엇을 보는지: 화면 위치, 요청·응답 창의 요청, 로그 검색어, 시간 측정 방법.

## 6. 정리 (원상복구)
다른 시나리오에 영향을 주지 않게 되돌릴 것.

---- 아래는 수행자가 채움 ----

## 7. 수행 기록
| 환경 | 수행자 | 수행 일시 | 빌드(우리 main / internal/gaia 커밋) | 결과 |
| --- | --- | --- | --- | --- |
| dev | | | | 통과 / 실패 / 보류 |
| prd | | | | |

## 8. 실제 결과와 증빙
- 단계별 실제 결과 (예상과 다르면 무엇이 달랐는지)
- 증빙: 화면 캡처, 요청·응답 창의 응답 본문, request id, run id, executor 실행 ID, pr-batch run ID

## 9. 결함
| 결함번호 | 심각도(치명/높음/보통/낮음) | 요약 | 재현 단계 | 예상 | 실제 | 발생 시각 | request id / run id |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

## 작성 규칙

- **수행자 PC는 Windows입니다.** 화면(Chrome·Edge)으로 하는 절차를 먼저 쓰고, 명령이 꼭 필요하면 PowerShell 기준으로 씁니다. PowerShell의 `curl`은 다른 명령(Invoke-WebRequest)이라 `curl.exe`로 쓰고, 줄을 나눌 때는 `\`가 아니라 백틱(`` ` ``)을 씁니다. JSON 본문은 파일(`body.json`)로 저장해 `--data-binary "@body.json"`으로 보냅니다(따옴표가 깨지지 않음).
- **키 호출 시나리오는 관리자 화면 시스템 > API 호출 시험에서** 합니다. 시나리오를 고르면 경로·본문·헤더가 채워집니다. 키 원문은 저장되지 않으니 매번 붙여 넣습니다.

- **예상 결과는 판정 가능한 값으로.** "분석이 잘 됨"이 아니라 "run 상태 `succeeded`, 답변 아래 리포트·노트북 첨부 2개".
- **시간 기준이 있는 시나리오**(키 폐기 60초, 사용자 차단 30초 등)는 시작 시각과 확인 시각을 초 단위로 적습니다.
- **실패하면** 상황판 상태를 `실패`로 바꾸고 9절에 결함을 적은 뒤 결함번호를 상황판에 넣습니다. 고친 뒤 다시 하면 `재테스트`, 통과하면 `통과`.
- **증빙에는 비밀값을 넣지 않습니다.** API 키 원문, 쿠키, CSRF 토큰은 가리고 올립니다.
- **단독 수행** 시나리오는 시작 전에 공지하고, 끝나면 정리(6절)까지 마친 뒤 공지합니다.

## 샘플 1. RUN-01 브라우저 분석 요청 → 계획 승인 → 실행 → 리포트

| 항목 | 값 |
| --- | --- |
| 서비스구분 | 세션·run 실행 |
| 우선순위 | P0 |
| 화면 | O |
| 필요 권한 | 일반 |
| 단독 수행 | 아니오 |
| 연동 경로 | I1 I3 I5 |

**1. 목적** 사용자가 화면에서 분석을 요청하면 계획 승인을 거쳐 executor에서 실행되고, 결과 리포트가 답변에 붙는지 확인합니다.

**2. 사전 조건**
- 계정: 일반 사용자 A로 SSO 로그인 가능 (AUTH-01 통과)
- 데이터: 합성 nce 데이터 (PREP-10)
- 환경: executor·Redis 정상, 시스템 > 런타임 탭에 ACTIVE 런타임 1개 이상 (PREP-08)

**3. 수행 절차**
1. 우리 화면에 로그인합니다.
2. 왼쪽에서 프로젝트를 고르고 새 대화를 엽니다. 모델은 기본값, 코드 레벨은 비워 둡니다(기본 3).
3. "nce 데이터 불러와서 기술통계 보여줘"를 보냅니다.
4. "실행 계획 확인" 카드가 뜨면 첫 후보를 그대로 두고 **승인하고 실행**을 누릅니다. 빈 필수 입력이 표시되면 값을 채웁니다.
5. 답변이 끝날 때까지 기다립니다. "코드 실행 승인" 카드가 뜨면 승인합니다.
6. 우측 상단 **요청·응답** 창을 열어 SSE 이벤트를 확인합니다.
7. 왼쪽 메뉴 **실행 이력**에서 방금 실행을 엽니다.

**4. 예상 결과**
- 4: 카드 종류가 plan_approval, 후보 1개 이상
- 5: 진행 표시 후 답변 완료. 답변 아래 리포트(MD)와 노트북(IPYNB) 첨부가 있고 "보기"로 열림
- 6: 이벤트에 `execution_completed`와 `artifact`가 있고, 마지막에 run 상태 `succeeded`
- 7: 실행 상태 `SUCCEEDED`, 사용자 칸이 A의 소문자 사번, run (metadata.run_id)가 채팅 머리의 run id와 같음

**5. 확인 방법** 채팅 머리의 프로젝트·세션·run id(누르면 전체 복사), 요청·응답 창의 `/sessions/{id}/events`, 실행 이력 > 개요 탭.

**6. 정리** 없음 (세션은 남겨 두고 다른 시나리오의 증빙으로 써도 됨).

## 샘플 2. TEN-03 사용자 B 비활성화

| 항목 | 값 |
| --- | --- |
| 서비스구분 | tenant·사용자 |
| 우선순위 | P0 |
| 화면 | O |
| 필요 권한 | 관리자 |
| 단독 수행 | 예 (B 계정을 쓰는 다른 시나리오가 깨짐) |
| 연동 경로 | I1 I6 |

**1. 목적** 관리자가 사용자를 비활성화하면 30초 안에 SSO·키 접근이 모두 막히고, 그 사람의 배치가 pr-batch에서 꺼지는지 확인합니다.

**2. 사전 조건**
- 계정: 관리자, 일반 사용자 B
- B가 일정 있는 배치를 하나 켜 둔 상태 (B로 BAT-02 수행)
- B가 다른 브라우저(또는 시크릿 창)에 로그인해 있음
- 먼저 끝나야 할 시나리오: BAT-02 (B 계정으로)

**3. 수행 절차**
1. B 브라우저에서 배치 화면을 열어 B의 배치가 켜짐인지 확인합니다.
2. 관리자로 **시스템 > 사용자**에서 B의 사번을 검색합니다.
3. **비활성화**를 누르고 확인 창에서 승인합니다. 이때 시각을 초 단위로 적습니다.
4. 30초 뒤 B 브라우저에서 새로 고침합니다.
5. 관리자 화면에서 B 줄의 **배치 보기**를 누릅니다(비활성화 직후에는 자동으로 열림).

**4. 예상 결과**
- 3: "pr-batch에서 배치를 껐습니다" 알림, 사용자 목록에서 B가 "비활성". pr-batch가 답하지 않았으면 "배치 끄기 재시도 대기" 표시(5분 안에 사라져야 함)
- 4: B는 로그인 화면으로 가거나 오류(401/403)를 받음. 30초 안
- 5: B의 배치가 "꺼짐 · 사용자 비활성화", 꺼진 사유 `USER_DEACTIVATED`

**5. 확인 방법** 관리자 화면 요청·응답 창의 `PATCH /admin/users/{id}` 응답(`batches_disable_pending`), B 브라우저 요청·응답 창의 상태 코드, 배치 보기 목록 캡처.

**6. 정리** TEN-06(재활성화)로 이어서 수행합니다. 재활성화해도 배치는 자동으로 켜지지 않으므로 B가 다시 켜야 합니다.

## 샘플 3. AUTH-04 키 + X-User-Id로 내 정보 조회

| 항목 | 값 |
| --- | --- |
| 서비스구분 | 인증 |
| 우선순위 | P0 |
| 화면 | O (시스템 > API 호출 시험) |
| 필요 권한 | 관리자 (+ 운영: 감사 로그 조회) |
| 단독 수행 | 아니오 |
| 연동 경로 | I2 |

**1. 목적** 외부 호출자가 API 키와 `X-User-Id`로 우리 API를 부를 수 있고, 감사 로그에 누가 불렀는지 남는지 확인합니다.

**2. 사전 조건**
- 키: PREP-09에서 발급한 외부 tenant 키(`it-ext`). 원문은 테스트 담당에게서 받음
- 사번: 우리 DB에 있는 일반 사용자 A의 사번 (A가 한 번 로그인했어야 함)
- 수행자: 관리자 계정으로 우리 화면에 로그인

**3. 수행 절차**
1. **시스템 > API 호출 시험** 탭을 엽니다.
2. 시나리오에서 **AUTH-04 · 키 + X-User-Id로 내 정보**를 고릅니다. 방식 `GET`, 경로 `/api/v1/users/me`가 채워집니다.
3. **X-Api-Key**에 키 원문을 붙여 넣고, **X-User-Id**를 A의 사번으로 바꿉니다. "이 로그인의 쿠키도 보내기"는 꺼져 있어야 합니다.
4. **요청 보내기**를 누릅니다.
5. 결과의 request id를 적고, 운영 담당이 로그에서 `api_client_request`와 그 request id를 검색합니다.

**4. 예상 결과**
- 4: 상태 200, 응답 본문 `id`가 A의 소문자 사번
- 5: `api_client_request client=<키 이름> tenant=it-ext user=<사번> method=GET path=/api/v1/users/me status=200` 한 줄, 같은 request id

**5. 확인 방법** API 호출 시험 화면의 결과(상태, request id, 응답 본문) 캡처. 화면에는 키가 나오지 않습니다. 로그 검색 결과.

**화면을 쓸 수 없을 때 (Windows PowerShell)**
```
curl.exe -s -i "https://<host>/api/v1/users/me" `
  -H "X-Api-Key: <key>" `
  -H "X-User-Id: <사번>"
```
캡처할 때 명령 줄의 키는 가립니다.

**6. 정리** 없음.
