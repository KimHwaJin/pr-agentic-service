# BAT-11 일반키·마스터키의 배치 조회 범위와 X-User-Id 필수

| 항목 | 값 |
| --- | --- |
| 서비스구분 | BAT 배치 |
| 우선순위 | P1 |
| 화면 | O 우리 화면만 |
| 필요 권한 | 관리자 |
| 단독 수행 | 아니오 |
| 연동 경로 | I2 I6 |
| 11/01판 ID | - |

## 1. 목적
배치 게이트웨이도 key 종류와 관계없이 X-User-Id를 요구하고, 조회는 일반키면 그 사용자 것만, 마스터키면 tenant 전체(쿼리 user_id로 거르기), 쓰기는 X-User-Id 사용자로 되는지 확인합니다.

## 2. 사전 조건
- 우리 tenant 일반키·마스터키(PREP-09)
- 배치가 있는 A와 B(각자 BAT-02)
- A의 노트북 artifact ID(BAT-01)
- pr-batch 8dc99aa 이후(PREP-01)

## 3. 수행 절차
처음 수행하는 사람은 아래 3-1절 "화면 조작 안내"를 먼저 읽습니다. 번호 줄은 할 일이고, 그 아래 작은 항목은 실제로 누르고 입력하고 확인할 내용입니다. "※ 미확인"은 코드로 확인하지 못해 환경에서 한 번 확인이 필요한 내용입니다. 우리 화면(`/dev/`)은 테스트를 수행하기 위한 보조 도구이고 통합 테스트 대상이 아닙니다. 통과·실패는 서버 응답(상태 코드, 응답 본문, 이벤트)과 세 서비스의 기록으로 판정하고, 화면에 보이는 글자나 버튼은 그 값을 읽는 수단으로만 씁니다.

1. 관리자로 시스템 > API 호출 시험 탭을 엽니다. 직접 입력, GET /api/v1/batch/batches?limit=20을 우리 tenant 일반키, X-User-Id=A로 보냅니다.
   - 관리자로 로그인한 창에서 왼쪽 **시스템**을 누르고 위쪽 탭 **API 호출 시험**을 누릅니다.
   - A와 B가 각자 배치를 하나 이상 만들어 둔 상태여야 합니다. 두 사번을 준비합니다.
   - "시나리오" **직접 입력**을 고르고 "X-Api-Key 보내기"에 우리 tenant 일반키, "X-User-Id 보내기"에 A의 사번을 넣습니다. 방식 GET, 경로 `/api/v1/batch/batches?limit=20`으로 **요청 보내기**를 누릅니다.
   - **상태** 200이고 항목의 `user_id`가 모두 A인지 봅니다.
2. 경로 끝에 &user_id=<B의 사번>을 붙여 보냅니다.
   - 경로를 `/api/v1/batch/batches?limit=20&user_id=<B의 사번>`으로 고쳐 보냅니다. 403, `code` `FORBIDDEN`인지 봅니다.
3. 키를 마스터키로 바꾸고(X-User-Id=A) GET /api/v1/batch/batches?limit=20을 보냅니다.
   - 키 칸을 우리 tenant 마스터키로 바꿉니다. 경로를 `/api/v1/batch/batches?limit=20`으로 되돌려 보냅니다. 200이고 A와 B의 배치가 함께 나오는지 봅니다.
4. 경로 끝에 &user_id=<B의 사번>을 붙여 보냅니다.
   - 경로 끝에 `&user_id=<B의 사번>`을 붙여 보냅니다. 200이고 항목이 모두 B인지 봅니다.
5. X-User-Id 보내기를 끄고 마스터키로 3을 다시 보냅니다.
   - "X-User-Id 보내기" 체크를 끄고 경로를 `/api/v1/batch/batches?limit=20`으로 되돌려 보냅니다. 400, `code` `INVALID_IDENTITY`인지 봅니다.
   - 확인 후 "X-User-Id 보내기"를 다시 켜고 A의 사번이 들어 있는지 봅니다.
6. 마스터키, X-User-Id=A로 방식 POST, 경로 /api/v1/batch/scripts/from-notebook, 본문 {"artifact_id":"<A의 노트북 artifact ID>"}, 추가 헤더 {"Idempotency-Key": "it-bat11-nb-<시각>"}를 보냅니다. 이어서 일반키, X-User-Id=A로 GET /api/v1/batch/scripts를 보냅니다.
   - 마스터키, A의 사번인 채로 방식 POST, 경로 `/api/v1/batch/scripts/from-notebook`, 본문 `{"artifact_id": "<A의 노트북 artifact ID>"}`, 추가 헤더 `{"Idempotency-Key": "it-bat11-nb-<시각>"}`으로 보냅니다. 2xx이고 응답의 `user_id`가 A인지 봅니다. 스크립트 ID를 적습니다.
   - 키 칸을 일반키로 바꾸고 방식 GET, 경로 `/api/v1/batch/scripts`로 보냅니다(추가 헤더는 지워도 됩니다). 목록에 방금 스크립트 ID가 있는지 봅니다.

## 3-1. 화면 조작 안내

**접속과 로그인**
- 브라우저는 Chrome 또는 Edge를 씁니다. 주소창에 우리 화면 주소 `https://<host>/dev/`를 넣습니다. `<host>`는 환경마다 다르므로 테스트 담당이 공지한 dev 또는 prd 주소를 씁니다.
- 주소를 열면 회사 SSO 로그인 화면으로 넘어갑니다. 사번과 비밀번호로 로그인하면 우리 화면으로 돌아옵니다. "로그인하지 못했습니다"가 나오면 **다시 로그인**을 누르고, 그래도 안 되면 수행을 멈추고 운영 담당에게 알립니다.
- 지금 누구로 들어와 있는지는 화면 왼쪽 맨 아래 이름 칸에서 봅니다. 이름 아래에 사번이 있고, 칸을 누르면 "사번 … · 관리자" 또는 "사번 … · 일반 사용자"와 **로그아웃**이 나옵니다. 관리자는 이름 옆에 "관리자" 표시가 붙고 왼쪽 메뉴에 **시스템**이 보입니다.
- 이 문서의 계정 이름: **관리자**는 PREP-09에서 관리자로 로그인한 사번, **일반 A**와 **일반 B**는 테스트용 일반 사번 두 개입니다. 어느 사번이 A, B인지는 테스트 담당이 정해 둔 값을 씁니다.
- 사번을 입력하는 칸에는 항상 소문자로 넣습니다(예: `a10054`).

**화면 구성**
- 왼쪽 메뉴는 위에서부터 **새 대화**, **프로젝트**, **워크플로우**, **실행 이력**, **배치**, (관리자만) **시스템**입니다. 그 아래가 대화 목록, 맨 아래가 내 이름 칸입니다.
- 오류가 나면 화면 위쪽에 빨간 오류 메시지가 뜹니다. 메시지에는 오류 코드와 "요청 ID …"가 붙어 있고, 요청 ID를 누르면 복사됩니다. 결함을 적을 때 이 요청 ID를 함께 적습니다.

**ID와 사번 구하는 법**
- **프로젝트 ID, 세션 ID, run ID**: 대화를 열면 화면 위 대화 이름 옆에 "프로젝트 xxxxxxxx", "세션 xxxxxxxx", "런 xxxxxxxx" 꼬리표가 있습니다. 앞 8자리만 보이지만 꼬리표를 누르면 전체 ID가 복사됩니다("복사됨"으로 잠깐 바뀜). 메모장에 붙여 두고 씁니다.
- **사번**: 그 사람이 로그인한 화면의 왼쪽 맨 아래 이름 칸에 있습니다. 관리자는 **시스템 > 사용자**에서 이름으로 찾아 사번 칸을 볼 수도 있습니다.
- **기본 프로젝트 ID**: 요청·응답 창에서 `users/me`로 거른 뒤 `GET /api/v1/users/me` 줄의 응답 본문에서 `default_project_id` 값을 복사합니다.
- **실행 ID, 배치 ID 등 표의 짧은 ID**: 표에 8자리로 보이는 ID는 누르면 전체가 복사됩니다.

**시스템 > API 호출 시험 쓰는 법**
- 관리자로 로그인한 창에서 왼쪽 **시스템**을 누르고 위쪽 탭 중 **API 호출 시험**을 누릅니다. 다른 서비스가 API 키로 우리 서버를 부르는 것을 흉내 내는 화면입니다.
- **시나리오**: 목록에서 이 문서의 ID로 시작하는 항목을 고르면 방식, 경로, 본문, 아래 체크 상자가 자동으로 채워집니다. 목록에 없는 요청은 맨 위 **직접 입력**을 고르고 손으로 채웁니다. 시나리오를 다시 고르면 경로와 본문이 처음 값으로 돌아가니 주의합니다.
- **X-Api-Key 보내기**: 체크하고 아래 칸에 키 원문을 붙여 넣습니다. 글자는 가려져 보입니다. 키 원문은 PREP-09에서 발급해 테스트 담당이 보관하고 있으니 담당에게 받습니다. 어떤 키(우리 tenant 일반키, 우리 tenant 마스터키, 외부 tenant `it-ext` 키)를 써야 하는지는 사전 조건과 각 단계에 적혀 있습니다. 화면을 새로 고치면 칸이 비워지므로 다시 붙여 넣습니다.
- **X-User-Id 보내기**: 체크하고 아래 칸에 "누구를 대신해 부르는지"의 사번을 소문자로 넣습니다. 처음에는 지금 로그인한 관리자 사번이 들어가 있으니, 단계에서 "A의 사번"이라고 하면 반드시 바꿉니다.
- **추가 헤더 (JSON)**: 필요할 때만 `{"X-Project-Id": "…"}`처럼 넣습니다. 큰따옴표를 씁니다.
- **방식과 경로**: 왼쪽 목록에서 GET·POST·DELETE 등을 고르고, 오른쪽 칸에 `/api/v1/…` 경로를 넣습니다. 경로나 본문에 있는 `<project_id>` 같은 `<…>`는 꺾쇠까지 지우고 실제 값으로 바꿉니다.
- **본문 (JSON)**: POST 등에서 보낼 내용입니다. GET이면 무시됩니다.
- **이 로그인의 쿠키도 보내기**, **X-CSRF-Token 보내기**: 시나리오가 정한 대로 둡니다. 단계에서 따로 말할 때만 바꿉니다.
- **요청 보내기**를 누르면 아래에 결과가 나옵니다. **상태**(숫자, 성공은 초록·실패는 빨강), **보낸 시각**, **request id**, **보낸 헤더** 이름, **응답 본문**입니다. 보낸 시각은 UTC라서 한국 시간보다 9시간 이릅니다. 판정에는 상태 숫자와 응답 본문의 `code` 값을 봅니다.
- 증빙은 결과 부분을 캡처합니다. 키는 화면에 나오지 않습니다.

**배치 화면 쓰는 법**
- 왼쪽 **배치**를 누릅니다. 위쪽 탭은 **배치**, **스크립트**, **리포트**이고, 오른쪽 위에 **스크립트 등록**과 **새 배치** 버튼이 있습니다. "불러오지 못했습니다"가 나오면 pr-batch 쪽 문제이니 운영 담당에게 알립니다.
- **스크립트 등록** 창: "이름"(비우면 파일 이름), "노트북 파일 (.ipynb)" 또는 "세션 노트북 artifact ID" 중 하나를 넣고 **등록**을 누릅니다.
- **새 배치** 창: "이름", "프로젝트", "스크립트", "버전"(비우면 최신), "런타임", "일정"을 정하고 **만들기**를 누릅니다. 일정은 **수동 실행만**, **일정 간격 (분)**, **매일 정해진 시각**, **Cron** 중에서 고르고, 고르면 값 칸과 시작·종료 시각 칸이 나옵니다. 시간대는 한국 시간입니다. 만든 뒤 **켜기**를 눌러야 일정이 동작합니다.
- **배치** 탭 목록의 칸은 이름, 프로젝트, 스크립트, 일정, 다음 실행, 상태(켜짐 / 꺼짐)입니다. 줄 오른쪽에 **지금 실행**, **켜기** 또는 **끄기**(켤 수 없으면 사유 글자), **수정**, **삭제**가 있습니다.
- 배치 줄(이름)을 누르면 그 배치의 **실행 이력** 창이 열립니다. 탭은 **실행**과 **건너뛴 일정**이고, 오른쪽 위 **↻**가 새로 고침입니다. 자동으로 바뀌지 않으므로 상태 변화를 보려면 **↻**를 여러 번 누릅니다.
- 실행 이력 표의 칸은 상태, 실행, 방식, 시작, 종료, 소요, 노트북(**보기**), 리포트, (진행 중이면) **취소**입니다. 상태 옆에 ⚠나 ⓘ가 있으면 마우스를 올려 사유를 봅니다. 줄을 누르면 executor 실행 상세 창이 열립니다.
- **리포트** 탭은 배치 실행이 성공한 뒤 자동으로 만들어지는 리포트 목록입니다. 상태는 대기, 노트북 준비 대기, Agent 작성 중, 저장 중, 완료, 실패입니다. 줄을 누르면 리포트가 열립니다.

**끝난 뒤 기록**
- 각 단계에서 예상 결과와 비교할 화면을 캡처합니다(Windows는 Win+Shift+S). API 키 원문, 쿠키, CSRF 토큰이 보이면 가리고 올립니다.
- 이 페이지 7절 "수행 기록"에 환경, 수행자, 수행 일시, 빌드 커밋, 결과를 적고, 8절에 단계별 실제 결과와 증빙(캡처, 응답 본문, request id, run id, 실행 ID)을 붙입니다.
- 상황판(엑셀)에서 이 시나리오의 TC 줄마다 상태를 **통과** 또는 **실패**로 바꾸고 시작일자와 완료일자를 적습니다. 4절 예상 결과의 한 줄이 TC 하나입니다.
- 판정 근거는 서버가 준 값입니다. 4절 예상 결과에 화면 표시로 적힌 항목도 요청·응답 창의 응답 본문이나 이벤트에서 같은 값을 확인해 판정합니다. 화면만 이상하고(글자 깨짐, 버튼 위치, 새로 고침해야 보임 등) 서버 응답은 예상과 같으면 **통과**이고, 화면 문제는 결함으로 올리지 않고 테스트 담당에게 따로 알립니다.
- 화면으로 수행할 수 없게 되면(화면이 열리지 않음 등) 같은 요청을 **시스템 > API 호출 시험**이나 curl로 보내 수행해도 됩니다.
- 예상과 다르면 더 진행하지 말고 상태를 **실패**로 두고 9절에 결함(재현 단계, 예상, 실제, 발생 시각, request id)을 적은 뒤 결함번호를 상황판에 넣습니다.
