| 항목 | 값 |
| --- | --- |

## 1. 목적
테스트 대상 버전을 고정해, 결과와 결함이 어느 버전에서 나왔는지 알 수 있게 합니다.

## 2. 사전 조건
- 네 저장소(pr-agentic-service main·internal/gaia, executor, pr-batch, prj_re)의 배포 예정 커밋

## 3. 수행 절차
처음 수행하는 사람은 아래 3-1절 "화면 조작 안내"를 먼저 읽습니다. 번호 줄은 할 일이고, 그 아래 작은 항목은 실제로 누르고 입력하고 확인할 내용입니다. "※ 미확인"은 코드로 확인하지 못해 환경에서 한 번 확인이 필요한 내용입니다. 우리 화면(`/dev/`)은 테스트를 수행하기 위한 보조 도구이고 통합 테스트 대상이 아닙니다. 통과·실패는 서버 응답(상태 코드, 응답 본문, 이벤트)과 세 서비스의 기록으로 판정하고, 화면에 보이는 글자나 버튼은 그 값을 읽는 수단으로만 씁니다.

1. 각 저장소 담당에게 이번 환경에 배포할 커밋을 받습니다.
   - 저장소는 넷입니다: pr-agentic-service(main과 internal/gaia 두 브랜치), executor, pr-batch, prj_re. 각 저장소 담당에게 "이번 환경(dev 또는 prd)에 배포할 커밋 해시"를 물어 7자리 이상으로 받습니다.
   - 받은 값은 저장소 이름, 브랜치, 커밋 해시, 받은 날짜를 한 줄씩 적어 둡니다.
2. 통합테스트 계획 문서 요약의 기준 커밋과 상황판 비고에 적습니다.
   - 계획 문서(`docs/integration-test/integration-test-plan.md`) 맨 위 "요약"의 "기준 커밋" 줄을 받은 값으로 고칩니다.
   - 상황판(엑셀) "사전 준비" 시트의 PREP-01 줄 비고 칸에도 같은 값을 적고 상태를 **통과**로 바꿉니다.
3. 테스트 중 재배포는 결함 수정으로 병합된 커밋만 하고, 할 때마다 같은 곳에 새 커밋을 적습니다.
   - 테스트가 시작된 뒤에는 결함을 고친 커밋만 다시 배포합니다. 기능 추가 커밋이 섞이면 이미 통과한 시나리오를 다시 해야 합니다.
   - 재배포할 때마다 2번과 같은 두 곳에 새 커밋 해시와 배포 시각을 덧붙여 적습니다. 지우지 않고 아래에 추가합니다.
4. 아래 최소 커밋 이후여야 합니다(서비스 사이 계약이 맞물림): 우리 main `7058bde`·internal/gaia `fbf3721`, executor `c73ee52`(`runtime.kernel_id`, executions `user_id` 필터, `DELETE /runtime-targets/{id}`), pr-batch `8dc99aa`(`X-User-Id` 없는 tenant 전체 조회, `user_id` 필터, 응답 `user_id`).
   - 각 저장소에서 `git merge-base --is-ancestor <최소 커밋> <배포할 커밋>`을 실행해 오류 없이 끝나면(종료 코드 0) 최소 커밋 이후입니다. 오류가 나면 그 저장소는 더 새 커밋으로 배포해야 합니다.
   - 저장소가 PC에 없으면 저장소 담당에게 "이 커밋이 최소 커밋을 포함하는지" 확인을 요청합니다.

## 3-1. 화면 조작 안내

**운영 담당과 함께 할 때**
- "운영 담당이 …"로 시작하는 단계는 수행자가 직접 하지 않습니다. 배포 권한이 있는 운영 담당에게 요청하고, 끝났다는 답을 받은 뒤 다음 단계로 갑니다. 내부망에서는 kubectl을 쓸 수 없고, Deployment로 배포하는 사내 배포 시스템으로 배포합니다. 그래서 모든 변경은 "값을 고쳐 다시 배포"로 합니다. 아래는 운영 담당이 하는 일입니다.
- **우리 서비스 설정을 잠깐 바꾸기**: 설정값은 저장소 루트의 설정 파일에 있고 이미지에 함께 들어갑니다. 환경마다 다른 값(주소, 키, SSO 등)은 `config.<환경>.yml`(prd는 `config.prd.yml`), 모든 환경이 같이 쓰는 값은 `config.yml`에 있습니다. 단계에 적힌 이름의 줄을 찾아 원래 줄을 보관하고, 값을 고친 뒤 이미지를 다시 만들어 배포합니다.
- **환경 변수로 바꿔도 됩니다**: 같은 이름의 환경 변수가 설정 파일보다 우선합니다. Deployment의 `env`에 `이름=값`을 넣거나 `Dockerfile`에 `ENV 이름=값` 줄을 넣어 배포하고, 끝나면 지워 다시 배포합니다. 목록 값은 JSON으로 넣습니다(예: `SSO_ALLOWED_ORIGINS=["https://sso.example.com"]`).
- **되돌리기**: 보관한 원래 줄로 되돌려 다시 배포합니다. 테스트용으로 고친 값이 저장소의 main이나 internal/gaia에 남지 않게, 테스트용 변경은 끝난 뒤 커밋을 되돌리거나 별도 브랜치에서 배포합니다.
- **배포가 끝난 시각**: 새 버전이 떠서 요청을 받기 시작한 시각입니다. 배포 시스템의 완료 표시로 확인하고, 화면에서는 `https://<host>/dev/`가 다시 열리는지로 확인합니다. 시간 기준이 있는 시나리오는 이 시각을 초 단위로 적습니다.
- **재시작만**: 값을 바꾸지 않고 같은 버전을 다시 배포합니다.
- **서비스 내리기와 올리기**(executor, pr-batch): 배포 시스템에서 그 서비스를 잠깐 멈추고, 끝나면 다시 올립니다. 내려갔는지는 우리 화면에서 그 서비스에 가는 요청이 실패하는지로 확인할 수 있습니다(executor는 **실행 이력**, pr-batch는 **배치**).
- **로그 찾기**: 키바나(Kibana)에서 서비스와 시각 범위를 정하고 단계에 적힌 로그 이름으로 검색합니다. 로그 확인을 요청하는 사람은 검색어, 동작한 시각(초 단위), 있으면 request id나 run id를 전달합니다. 운영 담당은 찾은 줄을 그대로 복사해 주고, 수행자는 8절 증빙에 붙입니다.
- ※ 미확인: 배포 시스템의 화면 이름과 메뉴, 키바나에서 우리 서비스 로그를 고르는 방법(인덱스 이름)은 이 문서에 적지 못했습니다. executor와 pr-batch의 설정 방식은 각 담당의 방법을 따릅니다.
- "단독 수행: 예"인 시나리오는 다른 사람의 테스트를 깨뜨립니다. 시작 전에 테스트 채널에 시작을 알리고, 6절 정리까지 끝낸 뒤 끝났다고 알립니다.

**끝난 뒤 기록**
- 각 단계에서 예상 결과와 비교할 화면을 캡처합니다(Windows는 Win+Shift+S). API 키 원문, 쿠키, CSRF 토큰이 보이면 가리고 올립니다.
- 이 페이지 7절 "수행 기록"에 환경, 수행자, 수행 일시, 빌드 커밋, 결과를 적고, 8절에 단계별 실제 결과와 증빙(캡처, 응답 본문, request id, run id, 실행 ID)을 붙입니다.
- 상황판(엑셀)에서 이 시나리오의 TC 줄마다 상태를 **통과** 또는 **실패**로 바꾸고 시작일자와 완료일자를 적습니다. 4절 예상 결과의 한 줄이 TC 하나입니다.
- 판정 근거는 서버가 준 값입니다. 4절 예상 결과에 화면 표시로 적힌 항목도 요청·응답 창의 응답 본문이나 이벤트에서 같은 값을 확인해 판정합니다. 화면만 이상하고(글자 깨짐, 버튼 위치, 새로 고침해야 보임 등) 서버 응답은 예상과 같으면 **통과**이고, 화면 문제는 결함으로 올리지 않고 테스트 담당에게 따로 알립니다.
- 화면으로 수행할 수 없게 되면(화면이 열리지 않음 등) 같은 요청을 **시스템 > API 호출 시험**이나 curl로 보내 수행해도 됩니다.
- 예상과 다르면 더 진행하지 말고 상태를 **실패**로 두고 9절에 결함(재현 단계, 예상, 실제, 발생 시각, request id)을 적은 뒤 결함번호를 상황판에 넣습니다.
