# TEN-01 외부 tenant `it-ext` 일괄 폐기 (BAT-10 배치가 켜진 상태)

| 항목 | 값 |
| --- | --- |
| 서비스구분 | TEN tenant·사용자 |
| 우선순위 | P0 |
| 화면 | 일부 화면 + 보조 확인 · 폐기·401은 화면, 외부 tenant 배치 상태는 pr-batch에서 확인 |
| 필요 권한 | 운영 |
| 단독 수행 | 예 |

## 1. 목적
외부 tenant를 통째로 폐기하면 키가 막히고, 그 tenant의 배치가 꺼지고, 이미 돌던 실행은 끝까지 가는지 확인합니다.

## 2. 사전 조건
- BAT-10의 it-ext 배치가 켜진 상태
- it-ext 키 원문
- **단독 수행**: it-ext 키를 쓰는 다른 시나리오를 먼저 끝냄

## 3. 수행 절차
처음 수행하는 사람은 아래 3-1절 "화면 조작 안내"를 먼저 읽습니다. 번호 줄은 할 일이고, 그 아래 작은 항목은 실제로 누르고 입력하고 확인할 내용입니다. "※ 미확인"은 코드로 확인하지 못해 환경에서 한 번 확인이 필요한 내용입니다. 우리 화면(`/dev/`)은 테스트를 수행하기 위한 보조 도구이고 통합 테스트 대상이 아닙니다. 통과·실패는 서버 응답(상태 코드, 응답 본문, 이벤트)과 세 서비스의 기록으로 판정하고, 화면에 보이는 글자나 버튼은 그 값을 읽는 수단으로만 씁니다.

1. API 호출 시험에서 it-ext 키로 AUTH-04를 보내 200인지 봅니다.
   - 단독 수행입니다. `it-ext` 키를 쓰는 시나리오(AUTH-04·05·06·09, EXEC-03·05, BAT-10)가 모두 끝났는지 상황판에서 확인하고, 테스트 채널에 시작을 알립니다.
   - 관리자 창에서 **시스템** > **API 호출 시험** > "시나리오" **AUTH-04 · 키 + X-User-Id로 내 정보**를 고릅니다(방식 GET, 경로 `/api/v1/users/me`).
   - "X-Api-Key 보내기"에 `it-ext` 키 원문, "X-User-Id 보내기"에 A의 사번을 넣고 **요청 보내기**를 누릅니다. **상태**가 200인지 봅니다.
2. **시스템 > API 키**에서 it-ext 키 줄의 **tenant 전체 폐기**를 누르고 확인합니다. 시각을 적습니다.
   - 위쪽 **API 키** 탭을 누릅니다. tenant 칸이 `it-ext`인 줄을 찾아 그 줄의 **tenant 전체 폐기**를 누릅니다. tenant가 `dtest-agent-service`인 줄에서 누르면 우리 키가 모두 끊기니 줄을 다시 확인합니다.
   - 확인 창에서 **확인**을 누르고, 누른 시각을 초 단위로 적습니다.
3. 알림 문구를 봅니다.
   - 알림 창이 뜨면 닫기 전에 캡처합니다.
   - 판정은 서버 응답으로 합니다. 요청·응답 창을 열고 **현재 대화만** 체크를 끕니다. `POST /api/v1/admin/api-clients/tenants/it-ext/revoke` 줄의 응답 본문에서 `revoked`(폐기한 키 수)가 1 이상이고 `batches_disabled`가 `true`인지 봅니다. pr-batch가 답하지 않았으면 `batches_disable_pending`이 `true`이고 알림이 "다시 시도하고 있습니다"로 나옵니다.
4. 60초 뒤 API 호출 시험에서 같은 요청을 다시 보냅니다.
   - 2번 시각에서 60초가 지나면 **API 호출 시험** 탭으로 돌아가 1번과 같은 요청을 다시 보냅니다. **상태**가 401인지 봅니다.
5. 운영 담당이 pr-batch에서 it-ext 배치의 상태를 봅니다(it-ext 배치는 우리 화면에 안 보임).
   - 운영 담당(또는 pr-batch 담당)에게 BAT-10에서 만든 배치 ID를 전달하고 pr-batch에서 그 배치가 꺼졌는지, `disabled_reason`이 `TENANT_REVOKED`인지 확인을 요청합니다.
   - 폐기 전에 제출돼 돌고 있던 실행이 있었다면 그 실행이 끝까지 갔는지도 함께 확인받습니다.

## 3-1. 화면 조작 안내

**접속과 로그인**
- 브라우저는 Chrome 또는 Edge를 씁니다. 주소창에 우리 화면 주소 `https://<host>/dev/`를 넣습니다. `<host>`는 환경마다 다르므로 테스트 담당이 공지한 dev 또는 prd 주소를 씁니다.
- 주소를 열면 회사 SSO 로그인 화면으로 넘어갑니다. 사번과 비밀번호로 로그인하면 우리 화면으로 돌아옵니다. "로그인하지 못했습니다"가 나오면 **다시 로그인**을 누르고, 그래도 안 되면 수행을 멈추고 운영 담당에게 알립니다.
- 지금 누구로 들어와 있는지는 화면 왼쪽 맨 아래 이름 칸에서 봅니다. 이름 아래에 사번이 있고, 칸을 누르면 "사번 … · 관리자" 또는 "사번 … · 일반 사용자"와 **로그아웃**이 나옵니다. 관리자는 이름 옆에 "관리자" 표시가 붙고 왼쪽 메뉴에 **시스템**이 보입니다.
- 이 문서의 계정 이름: **관리자**는 PREP-09에서 관리자로 로그인한 사번, **일반 A**와 **일반 B**는 테스트용 일반 사번 두 개입니다. 어느 사번이 A, B인지는 테스트 담당이 정해 둔 값을 씁니다.
- 사번을 입력하는 칸에는 항상 소문자로 넣습니다(예: `a10054`).

**화면 구성**
- 왼쪽 메뉴는 위에서부터 **새 대화**, **프로젝트**, **워크플로우**, **실행 이력**, **배치**, (관리자만) **시스템**입니다. 그 아래가 대화 목록, 맨 아래가 내 이름 칸입니다.
- 오류가 나면 화면 위쪽에 빨간 오류 메시지가 뜹니다. 메시지에는 오류 코드와 "요청 ID …"가 붙어 있고, 요청 ID를 누르면 복사됩니다. 결함을 적을 때 이 요청 ID를 함께 적습니다.

**ID와 사번 구하는 법**
- **프로젝트 ID, 세션 ID, run ID**: 대화를 열면 화면 위 대화 이름 옆에 "프로젝트 xxxxxxxx", "세션 xxxxxxxx", "런 xxxxxxxx" 꼬리표가 있습니다. 앞 8자리만 보이지만 꼬리표를 누르면 전체 ID가 복사됩니다("복사됨"으로 잠깐 바뀜). 메모장에 붙여 두고 씁니다.
- **사번**: 그 사람이 로그인한 화면의 왼쪽 맨 아래 이름 칸에 있습니다. 관리자는 **시스템 > 사용자**에서 이름으로 찾아 사번 칸을 볼 수도 있습니다.
- **기본 프로젝트 ID**: 요청·응답 창에서 `users/me`로 거른 뒤 `GET /api/v1/users/me` 줄의 응답 본문에서 `default_project_id` 값을 복사합니다.
- **실행 ID, 배치 ID 등 표의 짧은 ID**: 표에 8자리로 보이는 ID는 누르면 전체가 복사됩니다.

**요청·응답 창 보는 법**
- 화면 오른쪽 위 구석의 **요청·응답 N** 버튼을 누르거나 Ctrl+`(숫자 1 왼쪽 키)를 누르면 열립니다. 이 화면이 서버에 보낸 요청과 받은 응답이 최신 순으로 쌓입니다.
- 목록 한 줄은 시각, 방식(GET·POST 등), 경로, 상태 코드, 걸린 시간입니다. 줄을 누르면 오른쪽에 **요청 본문**, **응답 본문**(각각 **복사** 버튼), 접혀 있는 **헤더**가 나옵니다.
- 원하는 요청을 찾으려면 위쪽 "경로·메서드·상태로 거르기" 칸에 경로 일부(예: `users/me`)나 상태 코드(예: `403`)를 넣습니다.
- **현재 대화만**이 켜져 있으면 지금 열어 둔 대화의 요청만 보입니다. 채팅이 아닌 화면(시스템, 배치, 실행 이력)의 요청이 안 보이면 이 체크를 끕니다.
- **SSE**가 켜져 있으면 경로가 `/sessions/…/events`인 줄이 보입니다. 이 줄을 누르면 "받은 이벤트 N건"이 최신 순으로 나오고, 이벤트마다 종류(`run_status`, `hitl_request`, `execution_completed`, `artifact` 등)와 내용이 있습니다.
- **오류만**을 켜면 실패한 요청만 남고, **지우기**는 목록을 비웁니다. 확인하려는 동작 직전에 **지우기**를 누르면 찾기 쉽습니다.

**시스템 > API 호출 시험 쓰는 법**
- 관리자로 로그인한 창에서 왼쪽 **시스템**을 누르고 위쪽 탭 중 **API 호출 시험**을 누릅니다. 다른 서비스가 API 키로 우리 서버를 부르는 것을 흉내 내는 화면입니다.
- **시나리오**: 목록에서 이 문서의 ID로 시작하는 항목을 고르면 방식, 경로, 본문, 아래 체크 상자가 자동으로 채워집니다. 목록에 없는 요청은 맨 위 **직접 입력**을 고르고 손으로 채웁니다. 시나리오를 다시 고르면 경로와 본문이 처음 값으로 돌아가니 주의합니다.
- **X-Api-Key 보내기**: 체크하고 아래 칸에 키 원문을 붙여 넣습니다. 글자는 가려져 보입니다. 키 원문은 PREP-09에서 발급해 테스트 담당이 보관하고 있으니 담당에게 받습니다. 어떤 키(우리 tenant 일반키, 우리 tenant 마스터키, 외부 tenant `it-ext` 키)를 써야 하는지는 사전 조건과 각 단계에 적혀 있습니다. 화면을 새로 고치면 칸이 비워지므로 다시 붙여 넣습니다.
- **X-User-Id 보내기**: 체크하고 아래 칸에 "누구를 대신해 부르는지"의 사번을 소문자로 넣습니다. 처음에는 지금 로그인한 관리자 사번이 들어가 있으니, 단계에서 "A의 사번"이라고 하면 반드시 바꿉니다.
- **추가 헤더 (JSON)**: 필요할 때만 `{"X-Project-Id": "…"}`처럼 넣습니다. 큰따옴표를 씁니다.
- **방식과 경로**: 왼쪽 목록에서 GET·POST·DELETE 등을 고르고, 오른쪽 칸에 `/api/v1/…` 경로를 넣습니다. 경로나 본문에 있는 `<project_id>` 같은 `<…>`는 꺾쇠까지 지우고 실제 값으로 바꿉니다.
- **본문 (JSON)**: POST 등에서 보낼 내용입니다. GET이면 무시됩니다.
- **이 로그인의 쿠키도 보내기**, **X-CSRF-Token 보내기**: 시나리오가 정한 대로 둡니다. 단계에서 따로 말할 때만 바꿉니다.
- **요청 보내기**를 누르면 아래에 결과가 나옵니다. **상태**(숫자, 성공은 초록·실패는 빨강), **보낸 시각**, **request id**, **보낸 헤더** 이름, **응답 본문**입니다. 보낸 시각은 UTC라서 한국 시간보다 9시간 이릅니다. 판정에는 상태 숫자와 응답 본문의 `code` 값을 봅니다.
- 증빙은 결과 부분을 캡처합니다. 키는 화면에 나오지 않습니다.

**시스템 > API 키 쓰는 법**
- 관리자로 왼쪽 **시스템** > 위쪽 탭 **API 키**를 누릅니다. 표의 칸은 이름, tenant, 종류(일반 / 마스터), 키(앞부분만), 상태(사용 중 / 폐기), 마지막 사용, 발급입니다.
- **새 키 발급**을 누르면 창이 열립니다. "이름", "tenant", "이 서비스의 tenant로 발급합니다" 체크 상자, "종류"(일반키 / 마스터키), "설명 (선택)"을 채우고 **발급**을 누릅니다.
- 발급되면 같은 창에 "발급된 키"가 한 번만 보입니다. **복사**를 눌러 메모장 등 안전한 곳에 붙여 둡니다. 창을 닫으면 다시 볼 수 없습니다.
- 줄 오른쪽 버튼: **재발급**(같은 이름으로 새 키, 지금 키는 바로 끊김), **폐기**(그 키 하나), **tenant 전체 폐기**(그 tenant의 모든 키). 모두 확인 창이 한 번 뜨고 **확인**을 눌러야 실행됩니다. 되돌릴 수 없으니 줄의 이름과 tenant를 다시 확인하고 누릅니다.
- 폐기한 키는 상태가 "폐기"로 바뀌고 버튼이 사라집니다.

**운영 담당과 함께 할 때**
- "운영 담당이 …"로 시작하는 단계는 수행자가 직접 하지 않습니다. 클러스터 권한이 있는 운영 담당에게 요청하고, 끝났다는 답을 받은 뒤 다음 단계로 갑니다. 아래는 운영 담당이 쓰는 방법입니다. `<namespace>`는 환경의 네임스페이스로 바꿉니다.
- **우리 서비스 설정을 잠깐 바꾸기**: 설정값은 이미지에 들어 있는 `config.<환경>.yml`에서 읽지만, 같은 이름의 환경 변수가 있으면 환경 변수가 우선합니다. 그래서 테스트용 변경은 이미지를 다시 만들지 않고 Deployment의 환경 변수로 합니다. `kubectl -n <namespace> set env deployment/pr-agentic-service 이름=값`을 실행하면 Pod가 하나씩 새 값으로 다시 뜹니다. `kubectl -n <namespace> rollout status deployment/pr-agentic-service`가 "successfully rolled out"으로 끝나면 새 Pod가 모두 뜬 것입니다. 그 시각을 적습니다.
- **바꾸기 전에 지금 값 보관**: `kubectl -n <namespace> set env deployment/pr-agentic-service --list`로 지금 환경 변수를 봅니다. 바꾸려는 이름이 이미 목록에 있으면(예: PREP-03에서 환경 변수로 넣은 키) 그 값을 보관해 두고, 되돌릴 때 같은 명령으로 원래 값을 다시 넣습니다.
- **되돌리기**: 목록에 없던 이름은 `kubectl -n <namespace> set env deployment/pr-agentic-service 이름-`(이름 뒤에 빼기 기호)로 환경 변수를 지웁니다. 그러면 다시 설정 파일의 값을 씁니다. 되돌린 뒤에도 `rollout status`로 끝난 것을 확인합니다.
- **목록 값**은 JSON으로 넣습니다. 예: `SSO_ALLOWED_ORIGINS='["https://sso.example.com"]'`.
- **재시작만**: `kubectl -n <namespace> rollout restart deployment/pr-agentic-service`.
- **서비스 내리기와 올리기**(executor, pr-batch): `kubectl -n <namespace> get deployment`로 이름과 지금 Pod 수를 확인하고, `kubectl -n <namespace> scale deployment/<이름> --replicas=0`으로 내립니다. `kubectl -n <namespace> get pod`에서 그 서비스의 Pod가 없어지면 내려간 것입니다. 올릴 때는 `--replicas=<원래 수>`로 실행하고 `rollout status`로 확인합니다. 그 Deployment에 HPA가 걸려 있으면(`kubectl -n <namespace> get hpa`) Pod를 다시 올려 버리므로, 내리는 동안 HPA를 먼저 지우고 끝난 뒤 다시 적용합니다. 우리 서비스에는 HPA(최소 2개)가 있습니다.
- **로그 찾기**: `kubectl -n <namespace> logs -l app=pr-agentic-service --prefix --since=10m --tail=-1 | grep <검색어>`. 로그 확인을 요청하는 사람은 검색어(단계에 적힌 로그 이름), 동작한 시각(초 단위), 있으면 request id나 run id를 전달합니다. 운영 담당은 찾은 줄을 그대로 복사해 주고, 수행자는 8절 증빙에 붙입니다.
- ※ 미확인: 위 명령은 저장소의 `deploy/kubernetes/deployment.yml`(Deployment 이름 `pr-agentic-service`, 레이블 `app=pr-agentic-service`) 기준입니다. 내부망에서 이름이 다르거나, kubectl을 직접 못 쓰고 배포 파이프라인으로만 배포한다면 같은 환경 변수를 배포 설정의 `env`에 넣어 배포합니다. executor와 pr-batch의 Deployment 이름, 설정 방식, 사내 로그 도구는 각 담당의 방법을 따릅니다.
- "단독 수행: 예"인 시나리오는 다른 사람의 테스트를 깨뜨립니다. 시작 전에 테스트 채널에 시작을 알리고, 6절 정리까지 끝낸 뒤 끝났다고 알립니다.

**끝난 뒤 기록**
- 각 단계에서 예상 결과와 비교할 화면을 캡처합니다(Windows는 Win+Shift+S). API 키 원문, 쿠키, CSRF 토큰이 보이면 가리고 올립니다.
- 이 페이지 7절 "수행 기록"에 환경, 수행자, 수행 일시, 빌드 커밋, 결과를 적고, 8절에 단계별 실제 결과와 증빙(캡처, 응답 본문, request id, run id, 실행 ID)을 붙입니다.
- 상황판(엑셀)에서 이 시나리오의 TC 줄마다 상태를 **통과** 또는 **실패**로 바꾸고 시작일자와 완료일자를 적습니다. 4절 예상 결과의 한 줄이 TC 하나입니다.
- 판정 근거는 서버가 준 값입니다. 4절 예상 결과에 화면 표시로 적힌 항목도 요청·응답 창의 응답 본문이나 이벤트에서 같은 값을 확인해 판정합니다. 화면만 이상하고(글자 깨짐, 버튼 위치, 새로 고침해야 보임 등) 서버 응답은 예상과 같으면 **통과**이고, 화면 문제는 결함으로 올리지 않고 테스트 담당에게 따로 알립니다.
- 화면으로 수행할 수 없게 되면(화면이 열리지 않음 등) 같은 요청을 **시스템 > API 호출 시험**이나 curl로 보내 수행해도 됩니다.
- 예상과 다르면 더 진행하지 말고 상태를 **실패**로 두고 9절에 결함(재현 단계, 예상, 실제, 발생 시각, request id)을 적은 뒤 결함번호를 상황판에 넣습니다.
