# PREP-05 internal/gaia만

| 항목 | 값 |
| --- | --- |
| 서비스구분 | PREP 사전 준비 |
| 우선순위 | P0 |
| 화면 | X 화면 밖 · gaia 설정 |
| 필요 권한 | 운영 |
| 단독 수행 | 아니오 |

## 1. 목적
내부망 gaia 이미지(internal/gaia)의 SSO와 템플릿 값을 채웁니다.

## 2. 사전 조건
- SSO 담당에게 받은 로그인 페이지·userinfo 주소와 응답 필드명

## 3. 수행 절차
처음 수행하는 사람은 아래 3-1절 "화면 조작 안내"를 먼저 읽습니다. 번호 줄은 할 일이고, 그 아래 작은 항목은 실제로 누르고 입력하고 확인할 내용입니다. "※ 미확인"은 코드로 확인하지 못해 환경에서 한 번 확인이 필요한 내용입니다. 우리 화면(`/dev/`)은 테스트를 수행하기 위한 보조 도구이고 통합 테스트 대상이 아닙니다. 통과·실패는 서버 응답(상태 코드, 응답 본문, 이벤트)과 세 서비스의 기록으로 판정하고, 화면에 보이는 글자나 버튼은 그 값을 읽는 수단으로만 씁니다.

1. `src/dtest/idp_login.py`의 `SSO_LOGIN_PAGE`·`USERINFO_URL`·`FIELDS`를 채웁니다.
   - internal/gaia 브랜치에서만 합니다. `src/dtest/idp_login.py`를 열어 `SSO_LOGIN_PAGE`(SSO 로그인 페이지 주소), `USERINFO_URL`(사용자 정보 조회 주소), `FIELDS`(응답에서 사번·이름·부서 등을 꺼낼 필드 이름)를 SSO 담당에게 받은 값으로 채웁니다.
   - SSO 담당에게 userinfo 응답 예시를 받아 `FIELDS`의 필드 이름이 응답과 글자 하나까지 같은지 비교합니다.
2. 템플릿 고정값 `PORT`, `PROJECT_NAME`, `SERVICE_NAME`과 `GAIA_DEPLOYMENT`를 채웁니다.
   - ※ 미확인: 이 값들이 들어가는 파일 위치는 gaia 배포 템플릿 쪽이라 여기서 확인하지 못했습니다. gaia 배포 담당의 안내를 따릅니다.
3. HCP·gaia 의존성을 추가하고 `uv lock`을 다시 만듭니다.
   - ※ 미확인: 추가할 의존성 이름과 사내 패키지 저장소 설정은 내부망 환경 것이라 확인하지 못했습니다.
   - 의존성을 추가한 뒤 저장소 루트에서 `uv lock`을 실행해 `uv.lock`을 다시 만들고, 이미지를 빌드해 기동 로그에 오류가 없는지 봅니다.

## 3-1. 화면 조작 안내

**운영 담당과 함께 할 때**
- "운영 담당이 …"로 시작하는 단계는 수행자가 직접 하지 않습니다. 서비스 중지·기동, 설정 변경·재배포, 로그·DB·Redis 조회 권한이 있는 운영 담당에게 요청하고, 끝났다는 답을 받은 뒤 다음 단계로 갑니다.
- 로그 확인을 요청할 때는 검색어(단계에 적힌 로그 이름), 동작한 시각(초 단위), 그리고 있으면 request id나 run id를 함께 전달합니다. 운영 담당은 찾은 로그 줄을 그대로 복사해 주고, 수행자는 그것을 8절 증빙에 붙입니다.
- ※ 미확인: 로그를 어디서 어떻게 검색하는지와 서비스를 내리고 올리는 명령은 환경(클러스터, 네임스페이스, 로그 도구)마다 달라 이 문서에 적지 못했습니다. 운영 담당이 쓰는 방법을 따릅니다.
- 화면 칸에 "단독 수행: 예"인 시나리오는 다른 사람의 테스트를 깨뜨립니다. 시작 전에 테스트 채널에 시작을 알리고, 6절 정리까지 끝낸 뒤 끝났다고 알립니다.

**끝난 뒤 기록**
- 각 단계에서 예상 결과와 비교할 화면을 캡처합니다(Windows는 Win+Shift+S). API 키 원문, 쿠키, CSRF 토큰이 보이면 가리고 올립니다.
- 이 페이지 7절 "수행 기록"에 환경, 수행자, 수행 일시, 빌드 커밋, 결과를 적고, 8절에 단계별 실제 결과와 증빙(캡처, 응답 본문, request id, run id, 실행 ID)을 붙입니다.
- 상황판(엑셀)에서 이 시나리오의 TC 줄마다 상태를 **통과** 또는 **실패**로 바꾸고 시작일자와 완료일자를 적습니다. 4절 예상 결과의 한 줄이 TC 하나입니다.
- 판정 근거는 서버가 준 값입니다. 4절 예상 결과에 화면 표시로 적힌 항목도 요청·응답 창의 응답 본문이나 이벤트에서 같은 값을 확인해 판정합니다. 화면만 이상하고(글자 깨짐, 버튼 위치, 새로 고침해야 보임 등) 서버 응답은 예상과 같으면 **통과**이고, 화면 문제는 결함으로 올리지 않고 테스트 담당에게 따로 알립니다.
- 화면으로 수행할 수 없게 되면(화면이 열리지 않음 등) 같은 요청을 **시스템 > API 호출 시험**이나 curl로 보내 수행해도 됩니다.
- 예상과 다르면 더 진행하지 말고 상태를 **실패**로 두고 9절에 결함(재현 단계, 예상, 실제, 발생 시각, request id)을 적은 뒤 결함번호를 상황판에 넣습니다.
