# 인수인계 문서

기준: internal/gaia 브랜치, 2026-11-22.

이 문서는 인수인계 문서 세트의 첫 장입니다. 서비스가 무엇인지, 운영자가 반드시 알아야 할 것이 무엇인지, 현재 어떤 상태로 넘기는지를 정리합니다. 주소, 계정, 키 같은 환경별 실제 값은 적지 않고 서비스 이름과 설정 키 이름으로 가리킵니다.

## 1. 한 쪽 요약

### 1.1 서비스

pr-agentic-service는 사내 데이터 분석 Agent 서비스입니다.

- 사용자가 채팅으로 분석을 요청하면 Agent가 분석 계획을 세워 승인을 받고, 분석 코드를 executor에 보내 실행하고, 결과를 읽어 리포트를 씁니다.
- 사용자, 프로젝트, 세션 계층을 가진 채팅 API입니다. 인증은 사내 SSO입니다.
- 다른 서비스와 에이전트가 executor와 pr-batch를 쓸 때 거치는 입구(게이트웨이)이기도 합니다. API 키를 우리가 발급합니다.
- pr-batch의 배치 실행이 성공하면 그 결과를 분석한 리포트를 자동으로 만듭니다.
- gaia 채팅 화면에서 workflow `dtest.analyst`로도 쓸 수 있습니다.

### 1.2 구성

| 항목 | 내용 |
| --- | --- |
| 언어, 프레임워크 | Python 3.11, FastAPI, LangGraph, LangChain, SQLAlchemy(비동기) |
| 실행 형태 | 인스턴스 하나가 프로세스 하나. 그 안에 API와 백그라운드 작업이 함께 있음. 같은 인스턴스를 여러 개 띄움 |
| 규모 | 인스턴스 2~4개, 사용자 약 200명 기준 설계 |
| 저장소 | PostgreSQL(앱 테이블 19개 + LangGraph 체크포인트), Redis(로그인 세션, 실시간 이벤트), 공유 저장소(executor와 파일 교환) |
| 연결 서비스 | SSO, LLM 게이트웨이, 임베딩 게이트웨이, executor, pr-batch, Phoenix(선택) |
| 코드 위치 | 내부망 레포의 `src/dtest/` (gaia 템플릿 구조) |

### 1.3 운영자가 꼭 알아야 할 10가지

1. **Redis는 executor와 같은 서버, 같은 DB 번호여야 합니다.** 다르면 오류 없이 분석이 단계마다 2분씩 늦어집니다.
2. **Redis는 환경마다 standalone 또는 Sentinel입니다. `REDIS_MODE`를 그 환경의 구성에 맞춥니다.** Sentinel 구성의 노드를 standalone으로 직접 가리키면 장애 전환 뒤 `READONLY`로 멈춥니다.
3. **지금 dev와 prd가 같은 DB를 씁니다(곧 분리 예정).** 같은 데이터베이스를 쓰는 동안에는 한 환경의 worker가 다른 환경의 요청을 가져가 실행할 수 있고, dev의 마이그레이션이 prd 스키마도 바꿉니다.
4. **운영 마이그레이션은 배포 전에 따로 실행합니다.** 인스턴스 시작 때 자동 실행하다 실패하면 모든 인스턴스가 뜨지 못합니다.
5. **PostgreSQL 연결 수에는 예산이 있습니다.** 우리 인스턴스 하나가 최대 14개, DB 한도는 150이고 executor, pr-batch, 같은 DB를 쓰는 다른 환경과 나눠 씁니다. 교체 배포 중에는 일시적으로 늘어나므로 인스턴스가 3개 이상이면 하나씩 교체합니다.
6. **인스턴스 하나에 uvicorn worker는 1개입니다.** 처리량은 인스턴스 수로 늘립니다.
7. **가장 먼저 한계에 닿는 곳은 LLM 게이트웨이와 executor 제출입니다.** 우리 앱의 CPU가 아닙니다. CPU 사용률만으로는 LLM 대기로 밀리는 것을 알 수 없습니다.
8. **큰 요청(32MB)과 긴 연결(SSE)을 쓰는 서비스입니다.** 서비스 앞에서 크기나 시간을 더 작게 제한하면 413이나 실시간 화면 끊김으로 나타납니다.
9. **장애 때는 `/api/v1/healthz`, 키바나 로그의 요청 ID, `runs` 테이블 순서로 봅니다.** 사용자 화면의 8자리 오류 ID로 로그의 같은 줄을 찾을 수 있습니다.
10. **모든 코드 변경은 main과 internal/gaia 두 브랜치에 함께 넣습니다.** 마이그레이션 번호가 어긋나면 DB가 꼬입니다.

각 항목의 자세한 내용은 운영자 가이드 4장(주의할 점), 5장(부하 포인트), 6장(장애 대응)에 있습니다.

## 4. 저장소와 브랜치 운영

- `main`은 사외에서 개발하고 검증하는 브랜치, `internal/gaia`는 내부망에 넣는 브랜치입니다. 같은 기능을 두 구조로 유지합니다. 차이는 소스코드 설명서 13장에 있습니다.
- 모든 변경은 두 브랜치에 함께 반영합니다. `main`에서 작업했으면 `internal/gaia`에서 `git merge main`을 합니다.
- 내부망 레포로 가져가는 것은 `src/dtest/`, `src/workflows/dtest/`, `app.py`, `tests/`, `scripts/`, `deploy/`, `docs/`, `Dockerfile`, `pyproject.toml`, `uv.lock`, 설정 yml입니다.
- 내부망에서 채워야 하는 것은 다음과 같습니다.
  - `pyproject.toml`에 HCP 라이브러리와 gaia 기본 의존성 추가 후 `uv lock`
  - `config.yml`의 `PORT`(8080), `PROJECT_NAME`, `SERVICE_NAME`
  - `config.{dev,stg,prd}.yml`의 `<...>` 자리 전부. 하나라도 남으면 기동하지 않습니다.
  - `src/dtest/idp_login.py`의 SSO 주소와 필드 대응

내부망에서는 이 코드를 깃랩에 올리고, 설정 파일에 실제 값을 채운 뒤 배포합니다.

## 6. 계정과 키

| 항목 | 방식 |
| --- | --- |
| DB, Redis 등 자원 | 사내 서비스형 플랫폼에서 운영자가 만들고 접속 정보를 받음 |
| DB 계정 | 마스터 계정 하나를 서비스와 운영자가 함께 씀 |
| 서비스가 쓰는 키와 비밀번호 | `config.{env}.yml`에 적어 내부망 깃랩에 올리고 배포. 대상은 `DATABASE_URL`, `REDIS_URL` 또는 `REDIS_SENTINEL_*`, `LLM_API_KEY`, `EXECUTOR_API_KEY`, `EXECUTOR_ADMIN_API_KEY`, `BATCH_API_KEY`, `PHOENIX_API_KEY` |
| `EXECUTOR_API_KEY`, `BATCH_API_KEY` | executor와 pr-batch가 발급. 상대 서비스 설정에는 이 키의 SHA-256 해시가, 우리 설정에는 원문이 들어감 |
| 우리가 발급하는 API 키 | 서비스의 관리자 화면에서 발급. 원문은 발급 때 한 번만 보이고 DB에는 해시만 남음 |
| 서비스의 관리자 역할 | `ADMIN_EMPLOYEE_IDS`에 사번을 넣거나 `scripts/set_user_role.py`로 지정 |
| 로그 조회 | 키바나 |

`config.{dev,stg,prd}.yml`의 실제 값은 내부망 깃랩 밖으로 옮기지 않습니다. 사외 저장소의 같은 파일에는 `<...>` 자리 표시만 있고, 자리 표시가 남아 있으면 서비스가 기동을 거부합니다.

## 7. 미결 사항과 알려진 문제

### 7.1 알려진 문제 (2026-11-19 로컬 자체 수행에서 발견, 2026-11-22 기준 미조치)

| # | 내용 | 영향 |
| --- | --- | --- |
| 1 | 커널이 닫힌 뒤 Agent가 임의 값(`np.random`)으로 데이터를 만들어 분석을 이어 간 사례(RUN-19). 관측값이 앞 3행만 보여 모델이 알아채지 못함 | 결과 신뢰성. 가장 중요 |
| 2 | executor가 내려가 있을 때 run이 `failed`가 아니라 `succeeded`로 끝남(OPS-01) | 장애가 화면에서 성공으로 보임 |
| 3 | 다른 tenant 키로 노트북에서 배치 스크립트를 등록하면 우리 tenant로 들어감 | tenant 분리 |
| 4 | 코드 레벨 4에서도 계획 카드가 표시됨 | 기대 동작과 다름 |
| 5 | 등록한 워크플로우가 잘 추천되지 않음. Agent가 워크플로우 검색을 드물게 부름 | 워크플로우 재사용률 |

### 7.2 executor 담당에게 요청한 것 (2026-11-22 부하 테스트)

| # | 내용 |
| --- | --- |
| 1 | 실행 제출(`POST /executions`)이 동시 요청에서 초 단위로 느려짐. 처리량 초당 3~7건. 게이트웨이를 거치지 않고 직접 보내도 같음 |
| 2 | 실행 목록 조회가 대기 중인 실행이 있을 때 간헐적으로 500(`KeyError`) |
| 3 | 부하 중 메모리 한도로 런타임 배정이 12~13초씩 멈춤 |

상세한 측정값과 재현 방법은 `docs/reviews/executor-load-test-2026-11-22.md`에 있습니다.

### 7.3 구조상 알아 둘 제약

- 분석 skill과 tool의 `assets/` 내용은 예시 수준입니다. 실제 분석 품질은 별도 담당의 tool에 달려 있습니다.
- 프로젝트 공유 기능은 없습니다. 테이블(`project_members`)만 준비되어 있습니다.
- LLM 서빙 인프라(prefix caching 등)는 우리가 바꿀 수 없는 전제입니다. 성능 개선은 Agent 쪽에서 합니다.
- 사외 로컬의 LLM 게이트웨이와 내부망 배포 환경의 모델 구성은 다릅니다. 로컬에서 본 모델 동작이 내부망과 같다고 가정하지 않습니다.
- messages, runs, batch_report_jobs에는 자동 삭제가 없습니다. 장기 운영 시 보존 정책을 정해야 합니다.
- 지표 대시보드와 경보가 없습니다. 상태 확인 방법은 운영자 가이드 7.2절에 있습니다.
- dev와 prd가 같은 DB를 쓰는 동안의 제약은 운영자 가이드 4.3절에 있습니다.
- gaia 관련 통합테스트 시나리오는 이번 범위에서 제외되어 수행하지 않았습니다.
